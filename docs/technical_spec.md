# Technical Specification — Learning Grader ETL

## 1. Цель проекта

Разработать ETL-приложение на Python для получения статистики попыток пользователей учебной платформы через API, проверки и преобразования данных, загрузки результатов в PostgreSQL и формирования аналитической отчётности.

Приложение должно обеспечивать:

- автоматическое создание базы данных и таблиц при их отсутствии;
- извлечение исторических данных за заданные временные интервалы;
- проверку и преобразование исходных записей;
- сохранение корректных данных в PostgreSQL;
- повторный запуск без дублирования записей;
- восстановление загрузки после ошибок API;
- сохранение некорректных записей и сведений об ошибках;
- расчёт ежедневной статистики;
- выгрузку статистики в Google Sheets;
- отправку уведомлений о результатах выполнения;
- логирование основных этапов ETL.

**Источник данных:** https://api.itresume.ru/statistics/

## 2. Технологии

В проекте используются:

- Python 3.12;
- PostgreSQL;
- Requests — HTTP-запросы к API;
- psycopg 3 — взаимодействие с PostgreSQL;
- python-dotenv — загрузка переменных окружения;
- Google Sheets API — обновление аналитической таблицы;
- Google Drive API — поиск существующей Google-таблицы;
- Google OAuth 2.0 — авторизация пользователя;
- Telegram Bot API — отправка уведомлений;
- SMTP с OAuth2 (XOAUTH2) — отправка email-уведомлений;
- pytest — автоматизированное тестирование;
- Ruff — линтинг, форматирование и сортировка импортов.

Для работы с Google API используются библиотеки `google-api-python-client`, `google-auth` и `google-auth-oauthlib`.

Зависимости приложения определены в `requirements.txt`, инструменты разработки — в `requirements-dev.txt`.

## 3. Архитектура

Основные этапы обработки:

**Initialization → Extract → Transform → Rejected Records → Load → State → Statistics → Google Sheets → Notifications**

Обработка исторических периодов организована отдельно от формирования аналитической отчётности и отправки уведомлений.

### 3.1. Оркестрация

`main.py` — точка входа приложения.

Класс `GraderETL` отвечает за:

- инициализацию компонентов ETL;
- проверку и создание базы данных и таблиц;
- запуск загрузки исторических данных;
- расчёт ежедневной статистики;
- обновление Google Sheets;
- отправку итоговых уведомлений;
- обработку ошибок верхнего уровня;
- логирование общего времени выполнения.

Модуль `src/pipeline.py` содержит класс `GraderPipeline`, который управляет обработкой исторических периодов.

`GraderPipeline` координирует:

- формирование групп временных интервалов;
- параллельное получение данных из API;
- последовательное преобразование и сохранение результатов;
- пропуск ранее загруженных периодов;
- сохранение ошибок API;
- контроль непрерывности успешно обработанной истории;
- сбор статистики выполнения текущего запуска.

### 3.2. Database Initialization

Модуль `src/database.py` содержит класс `DatabaseInitializer`.

При запуске приложения:

1. Выполняется подключение к служебной базе PostgreSQL `postgres`.
2. Проверяется существование целевой базы данных.
3. Если база отсутствует, она создаётся.
4. Выполняется SQL-скрипт инициализации таблиц и индексов.

Структура таблиц определяется файлом `sql/create_tables.sql`.

Повторная инициализация не должна удалять ранее загруженные данные.

### 3.3. Extract

Модуль `src/extract.py` получает данные из API за заданные временные интервалы.

Предусмотрены:

- извлечение данных за отдельные сутки UTC;
- параллельное выполнение запросов;
- ограничение количества одновременных запросов;
- тайм-ауты HTTP-запросов;
- повторные попытки при предусмотренных ошибках API;
- передача полученных записей на этап Transform.

Для демонстрационного запуска используется два параллельных запроса.

Параллельность применяется на этапе получения данных. Обработка и сохранение результатов выполняются с учётом порядка исторических периодов.

### 3.4. Transform

Модуль `src/transform.py` содержит класс `GraderTransformer`.

Он проверяет полученные записи и преобразует их к структуре таблицы `grader_attempts`.

Основные операции:

- проверка структуры исходной записи;
- проверка непустого строкового идентификатора пользователя;
- удаление пробелов по краям `lti_user_id`;
- проверка допустимых значений `attempt_type`;
- проверка и преобразование `is_correct`;
- преобразование `created_at` из строки в `datetime`;
- безопасный разбор `passback_params` через `ast.literal_eval()`;
- извлечение необходимых параметров LTI;
- разделение корректных и некорректных записей.

Допустимые значения `attempt_type`:

- `run` — запуск кода;
- `submit` — отправка решения.

Допустимые значения `is_correct`:

- `True` и `1` преобразуются в `True`;
- `False` и `0` преобразуются в `False`;
- `None` сохраняется как `None`.

Отсутствующие отдельные параметры LTI получают значение `None`.

Подробные правила преобразования описаны в `docs/data_dictionary.md`.

### 3.5. Rejected Records

Модуль `src/rejected.py` содержит класс `RejectedRecords`.

Он сохраняет две категории информации:

- некорректные записи, отклонённые при преобразовании;
- ошибки получения данных из API.

Сведения сохраняются в JSON-файлы каталога `data/rejected/`.

**Некорректные записи**

Формат имени файла:

`YYYY-MM-DD.json`

Каждая запись содержит:

- `rejected_at` — время отклонения;
- `reason` — причину отклонения;
- `record` — исходную запись API.

**Ошибки API**

Формат имени файла:

`api_errors_YYYY-MM-DD.json`

Каждая ошибка содержит:

- `recorded_at` — время фиксации;
- `start` — начало периода;
- `end` — конец периода;
- `error_type` — тип исключения;
- `message` — сообщение об ошибке.

При повторном сохранении за одну дату новые сведения добавляются к существующим JSON-записям.

Некорректные записи не препятствуют загрузке остальных корректных записей периода.

### 3.6. Load

Модуль `src/load.py` содержит класс `GraderLoader`.

Он выполняет:

- загрузку корректных записей в `grader_attempts`;
- защиту от дублирования через `ON CONFLICT DO NOTHING`;
- подсчёт фактически добавленных записей с использованием `RETURNING`;
- регистрацию успешно обработанных периодов в `etl_periods`;
- обновление `etl_state`, если это допустимо;
- транзакционное выполнение операций загрузки.

Сохранение записей, периода и контрольной точки выполняется в рамках одной транзакции PostgreSQL.

Если API успешно вернул пустой набор данных, период регистрируется как обработанный.

### 3.7. State

Модуль `src/state.py` содержит класс `ETLState`.

Для хранения состояния используются две служебные таблицы:

- `etl_periods` — информация об отдельных успешно обработанных интервалах;
- `etl_state` — контрольная точка непрерывной загрузки.

Таблица `etl_periods` содержит:

- `pipeline_name`;
- `period_start`;
- `period_end`.

Таблица `etl_state` содержит:

- `pipeline_name`;
- `last_successful_end`.

При повторном запуске уже обработанные интервалы пропускаются.

Если один период завершился ошибкой API, а последующие периоды успешно загружены, `last_successful_end` не продвигается через пропущенный интервал.

После успешной повторной обработки пропуска контрольная точка может быть продвинута через следующую непрерывную последовательность ранее загруженных периодов.

Таким образом, ETL поддерживает возобновление исторической загрузки без повторного извлечения уже сохранённых периодов.

### 3.8. Statistics

Модуль `src/grader_statistics.py` содержит класс `GraderStatistics`.

Ежедневная статистика рассчитывается SQL-запросом непосредственно в PostgreSQL на основе таблицы `grader_attempts`.

Основные показатели:

- дата попытки;
- общее количество попыток;
- количество успешных попыток;
- процент успешности;
- количество уникальных пользователей;
- количество запусков кода (`run`);
- количество отправок решений (`submit`).

Процент успешности рассчитывается по формуле:

`successful_attempts / total_attempts * 100`

В знаменатель входят все зарегистрированные попытки, включая события типа `run`.

Результат округляется до двух знаков после запятой.

SQL-запрос использует `FILTER`, `COUNT(DISTINCT ...)` и `NULLIF()`.

### 3.9. Google Sheets

Модуль `src/google_sheets.py` содержит класс `GoogleSheetsManager`.

Он отвечает за:

- авторизацию через Google OAuth 2.0;
- использование ранее сохранённого OAuth-токена;
- обновление истёкшего токена при наличии refresh-токена;
- поиск существующей таблицы через Google Drive API;
- создание новой Google-таблицы при необходимости;
- сохранение идентификатора таблицы для следующих запусков;
- обновление ежедневной статистики.

Название Google-таблицы:

`Grader ETL — Daily Statistics`

Название рабочего листа:

`Daily Statistics`

Таблица содержит семь столбцов:

1. Дата.
2. Всего попыток.
3. Успешных попыток.
4. Процент успешности.
5. Уникальных пользователей.
6. Запусков кода.
7. Отправок решений.

При обновлении статистики очищаются существующие данные в столбцах `A:G`, после чего записывается актуальный набор строк.

Если статистика отсутствует, обновление Google Sheets не выполняется.

Ссылка на таблицу формируется по сохранённому идентификатору и включается в итоговые уведомления.

### 3.10. Notifications

Модули `src/telegram_notifier.py` и `src/email_notifier.py` отвечают за отправку итоговых отчётов.

Поддерживаются следующие статусы выполнения:

- `Успешно`;
- `Частично успешно`;
- `Ошибка`.

Уведомления содержат:

- статус выполнения;
- количество обработанных периодов;
- количество ошибок API;
- количество новых записей;
- ссылку на Google Sheets;
- сообщение об ошибке при аварийном завершении.

Для отправки email используется SMTP с авторизацией OAuth2 (XOAUTH2).

Поддерживаются защищённые соединения SSL и STARTTLS.

Ошибки отправки уведомлений фиксируются в логах и не приводят к откату ранее сохранённых данных PostgreSQL.

## 4. Запуск и конфигурация

Точка входа приложения:

```bash
python main.py
```

Настройки API, PostgreSQL, Google и уведомлений задаются через переменные окружения и локальные файлы авторизации.

Для настройки окружения предусмотрен файл `.env.example`.

Параметры исторического интервала, количество параллельных запросов и другие константы определяются в `src/constants.py`.

Основные параметры демонстрационной загрузки:

- `HISTORY_START` — начальная дата загрузки;
- `HISTORY_END` — конечная граница исторического интервала;
- `PERIOD_DAYS` — размер периода в сутках;
- `API_CONCURRENT_REQUESTS` — количество параллельных запросов;
- `LOAD_UNTIL_NOW` — режим расширения интервала до текущего времени.

Настройки подключения к PostgreSQL включают:

- `DB_HOST`;
- `DB_PORT`;
- `DB_NAME`;
- `DB_USER`;
- `DB_PASSWORD`.

Для Google OAuth используются локальные файлы с настройками авторизации и пользовательским токеном.

Идентификатор созданной или найденной Google-таблицы сохраняется отдельно.

Секреты, токены авторизации и локальные конфиденциальные файлы не должны попадать в Git.

## 5. Обработка исторических периодов

Историческая загрузка организована следующим образом:

1. При запуске выполняется инициализация PostgreSQL.
2. Из `etl_state` считывается последняя контрольная точка.
3. Из `etl_periods` загружается информация об уже обработанных интервалах.
4. Формируются суточные периоды UTC в пределах заданного исторического диапазона.
5. Периоды объединяются в группы с учётом ограничения параллельных запросов.
6. Данные извлекаются из API.
7. Результаты обрабатываются по периодам.
8. Ранее загруженные интервалы пропускаются.
9. Полученные записи проходят проверку и преобразование.
10. Отклонённые записи сохраняются отдельно.
11. Корректные записи загружаются в PostgreSQL.
12. Успешно обработанные периоды регистрируются в `etl_periods`.
13. Контрольная точка обновляется только при сохранении непрерывности успешно обработанных периодов.
14. После завершения исторической загрузки формируется ежедневная статистика.
15. Статистика выгружается в Google Sheets.
16. Отправляются итоговые уведомления.

### 5.1. Обработка ошибок отдельных периодов

Если запрос к API завершился ошибкой после предусмотренных повторных попыток:

- ошибка фиксируется в логах;
- сведения сохраняются в JSON;
- период не регистрируется как успешно обработанный;
- обработка остальных периодов может продолжаться;
- контрольная точка не продвигается через образовавшийся пропуск.

При следующем запуске ETL повторно обрабатывает пропущенные периоды, пропуская ранее успешно завершённые интервалы.

### 5.2. Защита от повторной загрузки

Защита реализована на двух уровнях:

- `etl_periods` предотвращает повторное извлечение уже обработанных интервалов;
- ограничения уникальности PostgreSQL совместно с `ON CONFLICT DO NOTHING` предотвращают повторную вставку конфликтующих записей.

Это обеспечивает возможность повторного запуска ETL без дублирования данных, подпадающих под ограничения уникальности.

## 6. Логирование и обработка ошибок

Модуль `src/logger.py` содержит класс `GraderLogger`.

Он обеспечивает запись событий:

- в консоль;
- в ежедневные лог-файлы.

Формат имени лог-файла:

`etl_YYYY-MM-DD.log`

Формат сообщения:

`YYYY-MM-DD HH:MM:SS | LEVEL | MESSAGE`

Логирование включает:

- запуск и завершение ETL;
- проверку и создание базы данных;
- обращения к API;
- количество полученных записей;
- результаты преобразования;
- количество корректных и отклонённых записей;
- результаты загрузки в PostgreSQL;
- ошибки API и преобразования;
- прогресс обработки исторических периодов;
- продолжительность отдельных этапов;
- общее время выполнения;
- результаты обновления Google Sheets;
- результаты отправки уведомлений.

### 6.1. Хранение логов

Срок хранения логов определяется константой `LOG_RETENTION_DAYS`.

Для проекта предусмотрено хранение журналов за 3 календарных дня, включая текущий день.

При инициализации логгера устаревшие файлы удаляются.

### 6.2. Обработка ошибок

Ошибки обрабатываются с учётом этапа ETL:

- некорректные отдельные записи исключаются из загрузки;
- ошибки API сохраняются отдельно и допускают повторную обработку периода;
- ошибки транзакций PostgreSQL приводят к откату соответствующей транзакции;
- ошибки Google Sheets фиксируются в логах и не отменяют сохранённые данные PostgreSQL;
- ошибки отправки уведомлений фиксируются отдельно.

Критические ошибки основного ETL-процесса приводят к завершению выполнения с ошибкой.

## 7. Тестирование

Для автоматизированного тестирования используется `pytest`.

Для изоляции внешних зависимостей и имитации ответов API применяется встроенная фикстура `monkeypatch`, позволяющая подменять функции, методы и переменные окружения.

Предусмотрены проверки:

- извлечения данных из API;
- проверки и преобразования записей;
- обработки некорректных данных;
- сохранения отклонённых записей;
- обработки ошибок API;
- инициализации PostgreSQL;
- транзакционной загрузки;
- защиты от дублирования;
- сохранения состояния ETL;
- пропуска ранее загруженных периодов;
- восстановления после ошибок API;
- расчёта ежедневной статистики;
- взаимодействия с Google Sheets;
- отправки уведомлений;
- оркестрации компонентов.

По результатам ранее выполненного запуска успешно пройдены 55 автоматизированных тестов.

Запуск тестов из корня проекта:

```bash
python -m pytest -q
```

Для проверки качества и форматирования кода используется Ruff.

```bash
python -m ruff check .
```

Для автоматического исправдения ошибок:

```bash
python -m ruff check . --fix
```

Автоматизированные тесты проверяют отдельные компоненты и сценарии работы приложения, но не заменяют сквозную проверку с реальным API, PostgreSQL и Google Sheets.

## 8. Демонстрационная загрузка и ограничения

Для сквозной проверки приложения выбран исторический интервал **с 1 по 31 мая 2023 года включительно**.

Параметры:

- начало: `2023-05-01 00:00:00 UTC`;
- окончание (исключительная граница): `2023-06-01 00:00:00 UTC`;
- размер периода: 1 сутки;
- количество периодов: 31;
- количество параллельных запросов к API: 2.

Выбор ограниченного периода обусловлен значительным объёмом исторических данных и временем выполнения запросов к внешнему API.

Демонстрационный запуск предназначен для проверки:

1. Автоматического создания базы данных и таблиц.
2. Извлечения данных из реального API.
3. Преобразования и проверки записей.
4. Сохранения корректных данных в PostgreSQL.
5. Регистрации обработанных периодов.
6. Сохранения контрольной точки.
7. Обработки ошибок и отклонённых записей.
8. Расчёта ежедневной статистики.
9. Обновления Google Sheets.
