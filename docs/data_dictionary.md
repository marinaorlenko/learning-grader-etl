# Data Dictionary — Learning Grader ETL

## 1. Назначение

Документ описывает структуру данных, получаемых из API статистики учебной платформы, правила их проверки, преобразования и хранения в PostgreSQL, а также формирование ежедневной аналитической статистики.

**Источник данных:** https://api.itresume.ru/statistics/

ETL-процесс предусматривает:

- извлечение исторических данных из API за суточные интервалы;
- проверку и преобразование полученных записей;
- загрузку корректных данных в PostgreSQL;
- автоматическое создание базы данных и таблиц при их отсутствии;
- сохранение состояния обработки;
- пропуск ранее успешно загруженных периодов;
- повторную обработку неуспешных периодов;
- сохранение отклонённых записей и информации об ошибках API;
- формирование ежедневной статистики для Google Sheets.

## 2. Исходные данные API

API возвращает записи о попытках пользователей учебной платформы.

| Поле | Тип данных API | Описание |
|---|---|---|
| `lti_user_id` | string | Идентификатор пользователя учебной платформы |
| `passback_params` | string | Строковое представление словаря с параметрами LTI |
| `is_correct` | boolean / integer / null | Результат проверки: `True` или `1` — успешная попытка, `False` или `0` — неуспешная, `null` — результат отсутствует |
| `attempt_type` | string | Тип попытки: `run` или `submit` |
| `created_at` | string | Дата и время создания попытки |

### 2.1. Параметры LTI

Поле `passback_params` содержит строковое представление словаря Python.

Из него извлекаются следующие параметры:

| Параметр | Описание |
|---|---|
| `oauth_consumer_key` | Ключ LTI-потребителя |
| `lis_result_sourcedid` | Идентификатор результата LTI |
| `lis_outcome_service_url` | URL сервиса передачи результата |

Для безопасного разбора строкового представления словаря используется `ast.literal_eval()`.

После разбора проверяется, что полученное значение является словарём.

Если один из перечисленных параметров отсутствует в словаре, ему присваивается значение `None`.

Отсутствие отдельного параметра LTI само по себе не является основанием для отклонения записи на этапе преобразования.

### 2.2. Типы попыток

В ETL обрабатываются два типа попыток:

- `run` — запуск пользовательского кода без отправки решения на проверку;
- `submit` — отправка решения на проверку.

Другие значения `attempt_type` считаются некорректными.

### 2.3. Преобразование результата попытки

Поле `is_correct` нормализуется к типу Python `bool` либо значению `None`.

| Исходное значение | После преобразования |
|---|---|
| `1` | `True` |
| `0` | `False` |
| `True` | `True` |
| `False` | `False` |
| `null` | `None` |

Другие значения отклоняются на этапе валидации.

## 3. Таблица PostgreSQL `grader_attempts`

Основная таблица содержит записи о попытках пользователей, успешно прошедшие преобразование и сохранённые в PostgreSQL.

| Поле | Источник | Описание |
|---|---|---|
| `user_id` | `lti_user_id` | Идентификатор пользователя после удаления пробелов по краям |
| `oauth_consumer_key` | `passback_params` | Ключ LTI-потребителя |
| `lis_result_sourcedid` | `passback_params` | Идентификатор результата LTI |
| `lis_outcome_service_url` | `passback_params` | URL сервиса передачи результата |
| `is_correct` | `is_correct` | Результат проверки, преобразованный к `True`, `False` или `None` |
| `attempt_type` | `attempt_type` | Тип попытки: `run` или `submit` |
| `created_at` | `created_at` | Дата и время попытки, преобразованные в `datetime` |

Точные SQL-типы, ограничения уникальности и индексы определены в `sql/create_tables.sql`.

### 3.1. Загрузка данных

Загрузка выполняется модулем `src/load.py`.

Для вставки записей используется SQL-конструкция `ON CONFLICT DO NOTHING`.

Она предотвращает повторную вставку записей, нарушающих установленные ограничения уникальности.

Для определения фактического количества добавленных записей используется `RETURNING`.

Таким образом, ETL различает количество записей, переданных на загрузку, и количество действительно добавленных записей.

### 3.2. Транзакционность

В рамках обработки одного периода выполняются:

1. Сохранение корректных записей в `grader_attempts`.
2. Регистрация успешно обработанного периода в `etl_periods`.
3. Обновление контрольной точки `etl_state`, если это допустимо.

Операции выполняются в общей транзакции PostgreSQL.

При ошибке транзакции изменения откатываются.

## 4. Таблица `etl_periods`

Таблица хранит информацию об успешно обработанных временных интервалах.

Каждый период определяется начальной и конечной границами.

| Поле | Описание |
|---|---|
| `pipeline_name` | Имя ETL-процесса |
| `period_start` | Начальная граница обработанного интервала |
| `period_end` | Конечная, исключительная граница обработанного интервала |

**Назначение таблицы:**

- учёт успешно обработанных периодов;
- пропуск периодов, загруженных ранее;
- выявление пропусков в истории загрузки;
- поддержка возобновления ETL после ошибок или прерывания;
- предотвращение повторных запросов к API за уже обработанные интервалы.

Успешно обработанный период сохраняется даже в том случае, если API вернул пустой набор данных.

Это означает, что отсутствие записей не считается ошибкой получения данных.

Информация о периоде записывается в PostgreSQL в рамках транзакции загрузки.

При повторной регистрации периода используется `ON CONFLICT DO NOTHING`.

## 5. Таблица `etl_state`

Таблица хранит контрольную точку последовательной обработки исторических данных.

| Поле | Описание |
|---|---|
| `pipeline_name` | Имя ETL-процесса, для которого хранится состояние |
| `last_successful_end` | Конечная граница последнего непрерывного диапазона успешно обработанных периодов |

В отличие от `etl_periods`, таблица `etl_state` не хранит каждый отдельный временной интервал.

Она определяет, до какого момента исторические данные были обработаны без пропусков.

### 5.1. Обработка пропусков

Если один из периодов завершился ошибкой API, а следующие периоды успешно загружены, `last_successful_end` не перемещается за границу пропущенного периода.

При этом последующие успешно обработанные периоды сохраняются в `etl_periods`.

При следующем запуске ETL:

1. Получает текущую контрольную точку.
2. Определяет периоды, требующие обработки.
3. Пропускает интервалы, уже зарегистрированные в `etl_periods`.
4. Повторно запрашивает неуспешные периоды.
5. После устранения пропуска продвигает контрольную точку через непрерывную последовательность успешно обработанных периодов.

Это позволяет возобновлять загрузку без повторного извлечения данных за уже завершённые интервалы.

## 6. Правила обработки данных

Историческая загрузка выполняется модулями `src/extract.py`, `src/transform.py`, `src/load.py` и `src/pipeline.py`.

Основные правила обработки:

1. Исторические данные извлекаются из API за суточные интервалы UTC.
2. Для ускорения загрузки допускается параллельное выполнение запросов к API.
3. Полученные записи преобразуются к структуре таблицы `grader_attempts`.
4. Поле `lti_user_id` проверяется на наличие непустой строки, после чего удаляются пробелы по краям.
5. Поле `attempt_type` должно содержать `run` или `submit`.
6. Поле `is_correct` должно содержать `True`, `False`, `0`, `1` или `None`.
7. Поле `created_at` преобразуется из строки в `datetime` согласно формату, определённому в `src/constants.py`.
8. Значение `passback_params` разбирается с помощью `ast.literal_eval()`.
9. Из `passback_params` извлекаются необходимые параметры LTI. Отсутствующие ключи получают значение `None`.
10. Корректные записи загружаются в PostgreSQL.
11. Некорректные записи исключаются из загрузки и сохраняются отдельно.
12. При успешной обработке интервала информация записывается в `etl_periods`.
13. Состояние `etl_state` обновляется с учётом непрерывности успешно обработанных интервалов.
14. При повторной загрузке записи, нарушающие ограничения уникальности, не добавляются повторно.

### 6.1. Отклонённые записи

Записи, не прошедшие проверку, сохраняются в каталоге `data/rejected/`.

Для каждого дня формируется JSON-файл с именем:

`YYYY-MM-DD.json`

Имя определяется датой начала обрабатываемого периода.

Каждая отклонённая запись содержит:

| Поле | Описание |
|---|---|
| `rejected_at` | Дата и время фиксации отклонения в UTC |
| `reason` | Причина отклонения записи |
| `record` | Исходная запись API |

Если файл за соответствующую дату уже существует, новые отклонения добавляются к ранее сохранённым.

Если отклонённых записей нет, файл не создаётся.

## 7. Обработка ошибок API

Ошибки получения данных из API обрабатываются отдельно от ошибок в содержимом отдельных записей.

Если запрос завершился неуспешно после предусмотренных повторных попыток:

- информация об ошибке сохраняется в JSON-файл каталога `data/rejected/`;
- неуспешный период не отмечается как загруженный;
- обработка остальных периодов может продолжаться;
- контрольная точка не продвигается через пропущенный интервал;
- при следующем запуске ETL неуспешный период может быть обработан повторно.

### 7.1. Файлы ошибок API

Файлы имеют формат имени:

`api_errors_YYYY-MM-DD.json`

Дата в имени соответствует началу неуспешного периода.

Каждая запись об ошибке содержит:

| Поле | Описание |
|---|---|
| `recorded_at` | Дата и время фиксации ошибки в UTC |
| `start` | Начало неуспешного интервала |
| `end` | Конец неуспешного интервала |
| `error_type` | Тип исключения Python |
| `message` | Текст сообщения об ошибке |

Если файл за соответствующую дату уже существует, новая информация добавляется к предыдущим ошибкам.

Сведения об ошибках также фиксируются в логах ETL.

### 7.2. Повторная обработка

При повторном запуске ETL использует таблицы `etl_periods` и `etl_state`, чтобы определить уже обработанные и пропущенные интервалы.

Успешно загруженные периоды не требуют повторного запроса к API.

Неуспешные периоды остаются доступными для повторной обработки.

## 8. Ежедневная статистика

На основе таблицы `grader_attempts` формируется ежедневная аналитическая статистика.

Расчёт выполняется SQL-запросом в модуле `src/grader_statistics.py`.

| Показатель | Расчёт |
|---|---|
| Дата | `created_at::date` |
| Всего попыток | `COUNT(*)` |
| Успешных попыток | `COUNT(*) FILTER (WHERE is_correct = TRUE)` |
| Процент успешности | Успешные попытки / все попытки × 100 |
| Уникальных пользователей | `COUNT(DISTINCT user_id)` |
| Запусков кода | `COUNT(*) FILTER (WHERE attempt_type = 'run')` |
| Отправок решений | `COUNT(*) FILTER (WHERE attempt_type = 'submit')` |

### 8.1. Расчёт процента успешности

Процент успешности рассчитывается по формуле:

`success_rate = successful_attempts / total_attempts * 100`

В знаменатель включаются все записи таблицы `grader_attempts`, в том числе события типа `run`.

Таким образом, показатель отражает долю успешных попыток среди всех зарегистрированных событий, а не только среди отправленных решений типа `submit`.

Результат округляется до двух знаков после запятой.

Для защиты от деления на ноль в SQL используется `NULLIF()`.

### 8.2. Выгрузка статистики

Результаты ежедневной агрегации подготавливаются для передачи в Google Sheets.

Статистика рассчитывается непосредственно в PostgreSQL, а не на основе исходных JSON-ответов API.

Это обеспечивает использование данных, фактически сохранённых в основной таблице.

## 9. Демонстрационный интервал загрузки

Для проверки полного ETL-процесса выбран период **с 1 по 31 мая 2023 года включительно**.

Границы интервала:

- начало: `2023-05-01 00:00:00 UTC`;
- окончание (исключительная граница): `2023-06-01 00:00:00 UTC`;
- размер одного периода: 1 сутки;
- количество суточных интервалов: 31.

Ограничение исторического интервала связано с объёмом данных и временем выполнения запросов к внешнему API.

Демонстрационная загрузка позволяет проверить:

1. Автоматическое создание базы данных PostgreSQL.
2. Создание таблиц и индексов.
3. Извлечение исторических данных из API.
4. Проверку и преобразование записей.
5. Сохранение корректных данных.
6. Обработку отклонённых записей.
7. Регистрацию успешно обработанных периодов.
8. Сохранение контрольной точки ETL.
9. Повторный запуск без дублирования данных.
10. Формирование ежедневной статистики.
11. Выгрузку результатов в Google Sheets.

Архитектура ETL позволяет расширить диапазон исторической загрузки без изменения логики извлечения, преобразования и сохранения данных.
