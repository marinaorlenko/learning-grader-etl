
# Learning Grader ETL

ETL-пайплайн на Python для автоматизированного сбора, проверки, преобразования и хранения статистики попыток решения заданий на образовательной платформе.

Приложение получает данные через REST API, загружает их в PostgreSQL, рассчитывает ежедневную статистику и обновляет Google Sheets. По итогам выполнения отправляет уведомления в Telegram и по электронной почте.

**Источник данных:** https://api.itresume.ru/statistics/

## Возможности

- Автоматическое создание базы данных PostgreSQL, таблиц и индексов.
- Получение статистики попыток через REST API.
- Параллельная загрузка данных за суточные интервалы UTC.
- Проверка структуры и значений исходных записей.
- Преобразование параметров LTI в отдельные поля.
- Сохранение некорректных записей и ошибок API в JSON.
- Загрузка корректных данных в PostgreSQL с защитой от дублирования.
- Транзакционное сохранение результатов загрузки.
- Учёт успешно обработанных периодов и состояния ETL.
- Повторная обработка пропущенных периодов при следующем запуске.
- Расчёт ежедневной статистики средствами SQL.
- Создание или поиск Google-таблицы и обновление статистики.
- Отправка итоговых уведомлений через Telegram и email.
- Логирование этапов обработки, ошибок и времени выполнения.
- Автоматическая очистка устаревших логов.

## Архитектура

Основная последовательность обработки:

    REST API
        |
        v
    Extract (параллельные запросы)
        |
        v
    Transform / Validation
        |
        +------------------> Rejected JSON
        |
        v
    Load
        |
        v
    PostgreSQL
        |
        +--> grader_attempts
        |
        +--> etl_periods
        |
        +--> etl_state
        |
        v
    Daily Statistics
        |
        v
    Google Sheets

    ETL Result
        |
        +--> Telegram
        |
        +--> Email

`main.py` управляет запуском приложения, инициализацией компонентов и итоговой отчётностью.

`src/pipeline.py` управляет обработкой исторических периодов, параллельными запросами, загрузкой данных и восстановлением пропущенных интервалов.

Для предотвращения повторной загрузки используются таблицы `etl_periods` и `etl_state`.

## Установка

### 1. Клонировать репозиторий

```bash
git clone https://github.com/marinaorlenko/learning-grader-etl.git
cd learning-grader-etl
```

### 2. Создать и активировать виртуальное окружение

Для macOS и Linux:

```bash
python3.12 -m venv venv
source venv/bin/activate
```

Если Python 3.12 доступен как `python3`, можно использовать `python3 -m venv venv`, предварительно проверив его версию.

### 3. Установить зависимости

Для запуска приложения:

```bash
python -m pip install -r requirements.txt
```

Для разработки и тестирования:

```bash
python -m pip install -r requirements-dev.txt
```

### 4. Настроить переменные окружения

```bash
cp .env.example .env
```

Заполнить параметры подключения к PostgreSQL, API и сервисам уведомлений.

Для работы с базой данных необходим запущенный сервер PostgreSQL. Пользователь должен иметь права на создание базы данных при первоначальной инициализации.

## Настройка Google Sheets

Для интеграции с Google Sheets необходимо:

1. Создать проект в Google Cloud Console.
2. Включить Google Sheets API и Google Drive API.
3. Настроить экран согласия OAuth.
4. Создать OAuth Client ID типа Desktop App.
5. Сохранить JSON-файл авторизации как `credentials/google_oauth.json`.
6. При первом обращении к Google API пройти авторизацию в браузере.

После авторизации токен сохраняется локально в `credentials/google_token.json`.

Идентификатор Google-таблицы сохраняется в `credentials/spreadsheet_id.json`, что позволяет обновлять одну и ту же таблицу при последующих запусках.

Приложение ищет существующую таблицу через Google Drive API либо создаёт новую.

Название документа:

`Grader ETL — Daily Statistics`

Название листа:

`Daily Statistics`

При выгрузке статистики существующие значения в столбцах `A:G` очищаются и заменяются актуальными данными.

**Ограничение:** если OAuth-приложение находится в режиме Testing, срок действия refresh token для соответствующих областей доступа может составлять семь дней. Для регулярной автономной работы необходимо обеспечить устойчивую авторизацию.

## Запуск ETL

```bash
python main.py
```

При запуске приложение:

1. Проверяет наличие базы данных PostgreSQL и при необходимости создаёт её.
2. Создаёт или проверяет необходимые таблицы и индексы.
3. Определяет сохранённое состояние загрузки.
4. Выявляет ранее успешно обработанные периоды.
5. Выполняет параллельные запросы к API за суточные интервалы UTC.
6. Проверяет и преобразует полученные записи.
7. Сохраняет некорректные записи отдельно.
8. Загружает корректные данные в PostgreSQL.
9. Сохраняет сведения об успешно обработанных периодах.
10. Обновляет состояние непрерывной загрузки.
11. Рассчитывает ежедневную статистику и обновляет Google Sheets.
12. Отправляет итоговые уведомления в Telegram и на email.

При ошибке API отдельный период может быть пропущен, а обработка следующих периодов продолжится.

При повторном запуске успешно загруженные периоды не запрашиваются повторно. Пропущенные интервалы обрабатываются заново.

### Настройка исторического интервала

Параметры загрузки определены в `src/constants.py`.

Для демонстрационного запуска выбран май 2023 года:

```python
HISTORY_START = datetime(2023, 5, 1, tzinfo=timezone.utc)
HISTORY_END = datetime(2023, 6, 1, tzinfo=timezone.utc)
PERIOD_DAYS = 1
LOAD_UNTIL_NOW = False
```

Конечная граница интервала не включается в загрузку.

Количество параллельных запросов:

```python
API_CONCURRENT_REQUESTS = 2
```

Для загрузки другого исторического интервала необходимо изменить соответствующие параметры конфигурации.

## Ежедневная статистика

Статистика рассчитывается SQL-запросом в PostgreSQL на основе таблицы `grader_attempts`.

Формируются следующие показатели:

- дата;
- всего попыток;
- успешных попыток;
- процент успешности;
- уникальных пользователей;
- запусков кода (`run`);
- отправок решений (`submit`).

Процент успешности рассчитывается как отношение количества успешных попыток к общему количеству попыток, включая события `run`.

Результат округляется до двух знаков после запятой.

## Тестирование

Для автоматизированных тестов используется `pytest`.

Подмена внешних зависимостей выполняется в том числе с помощью фикстуры `monkeypatch`.

Запуск всех тестов из корня проекта:

```bash
python -m pytest -q
```

Тесты охватывают:

- получение данных из API;
- обработку HTTP-ошибок и тайм-аутов;
- повторные запросы;
- преобразование и валидацию данных;
- работу с PostgreSQL;
- транзакционную загрузку;
- защиту от дублирования;
- сохранение состояния ETL;
- обработку пропущенных периодов;
- взаимодействие компонентов.

По результатам ранее выполненного запуска успешно пройдены 55 автоматизированных тестов. После изменений кода тесты необходимо запускать повторно.

Некоторые интеграционные проверки могут требовать настроенного окружения PostgreSQL.

## Логирование и обработка ошибок

Приложение записывает события выполнения в консоль и лог-файлы каталога `logs/`.

Файлы именуются по дате:

`etl_YYYY-MM-DD.log`

Срок хранения логов — 3 календарных дня, включая текущий день. Очистка устаревших файлов выполняется при инициализации логгера.

В логах фиксируются:

- начало и завершение ETL;
- запросы к API;
- количество полученных и обработанных записей;
- результаты записи в PostgreSQL;
- пропущенные и ошибочные периоды;
- длительность этапов обработки;
- обновление Google Sheets;
- отправка уведомлений.

Некорректные записи сохраняются в `data/rejected/YYYY-MM-DD.json`.

Ошибки API сохраняются в `data/rejected/api_errors_YYYY-MM-DD.json`.

Загрузка записей и сохранение сведений об успешно обработанных периодах выполняются транзакционно.

Ошибки Google Sheets и отправки уведомлений не отменяют успешно сохранённые данные PostgreSQL.

## Ограничения и статус проверки

Для демонстрации выбран ограниченный исторический интервал — май 2023 года.

Полная историческая выгрузка требует значительного количества запросов к API и времени выполнения. Поэтому для проверки архитектуры и функциональности используется один календарный месяц.

При этом ETL предусматривает возможность продолжения загрузки и расширения временного интервала без изменения основной архитектуры.

Автоматизированные тесты не заменяют сквозную проверку приложения с реальным API, PostgreSQL и Google Sheets.

Фактические результаты демонстрационного запуска необходимо оценивать отдельно по логам выполнения и состоянию базы данных.
